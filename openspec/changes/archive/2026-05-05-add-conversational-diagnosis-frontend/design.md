## Context

后端已经提供故障会话、证据上传、指标快照、诊断报告、恢复建议和复盘卡片等 API。当前前端只有最小表单演示，不能引导用户按排障过程逐步补充信息，也没有对重复提交、并发请求、错误恢复和闭环状态做明确表达。

本次变更面向 React 前端，目标是把后端诊断能力包装成对话式体验。用户不需要理解每个后端接口，只需要在页面中描述问题、按提示补充证据，并在诊断完成后查看报告、恢复建议和复盘结果。

约束包括：业务代码使用英文命名；必要注释尽量使用中文；业务代码必须补充单元测试；并发场景需要考虑线程命名、限流和配置开关。

## Goals / Non-Goals

**Goals:**

- 提供一个 React 对话式诊断工作台，作为诊断能力的主要前端入口。
- 编排现有后端 API，完成“创建会话 -> 收集证据 -> 触发诊断 -> 查看报告 -> 生成恢复建议 -> 模拟执行/生成复盘卡片”的闭环。
- 将对话消息、证据草稿、会话状态、诊断报告、恢复动作和错误提示纳入统一前端状态模型。
- 为诊断触发、证据上传和恢复动作生成提供防重复提交、限流和可配置开关。
- 为业务逻辑、API 编排和并发防护补充单元测试。

**Non-Goals:**

- 不重写后端诊断算法、规则检测器或 LLM 生成逻辑。
- 不实现真实生产恢复动作，前端只展示并触发后端已有的模拟执行能力。
- 不引入复杂多租户、登录鉴权、审批流或权限体系。
- 不建设独立聊天机器人后端；本次对话体验由前端状态机和现有诊断 API 共同完成。
- 不要求实时 WebSocket 推送；诊断过程可以通过按钮触发和请求结果更新完成。

## Decisions

1. **使用前端状态机表达诊断阶段。**

   采用明确的阶段枚举，例如 `idle`、`collectingEvidence`、`diagnosing`、`reviewingReport`、`recommendingRecovery`、`completed`、`failed`。相比在组件里散落多个布尔值，状态机更容易测试，也能避免并发请求导致按钮状态互相覆盖。

2. **使用轻量 API client 封装后端接口。**

   新增 `diagnosisApi` 模块封装 `/api/incidents` 相关请求，并保持函数命名为英文。组件只调用业务语义方法，例如 `createIncident`、`uploadEvidence`、`runDiagnosis`、`generateRecoveryActions`。这样可以在单元测试中 mock API client，而不是直接 mock 全局 `fetch` 的每个调用细节。

3. **对话消息由前端派生，不作为新的后端数据模型。**

   初版对话内容主要用于引导用户完成诊断流程，可由前端根据状态、用户输入和 API 结果派生。相比新增聊天记录表，这能减少后端改动并保持 MVP 聚焦。后续如需要审计或多人协作，再把消息持久化为独立能力。

4. **并发控制放在前端编排层，后端保持幂等和校验。**

   前端需要为每类长任务定义任务名，例如 `diagnosis-run:<sessionId>`、`evidence-upload:<sessionId>`、`recovery-generate:<sessionId>`。同名任务运行中时禁止再次触发，并通过限流保护高频点击。后端继续以会话 ID 校验资源归属。

5. **通过环境配置开关控制高级入口。**

   使用 Vite 环境变量，例如 `VITE_ENABLE_CONVERSATIONAL_DIAGNOSIS`、`VITE_DIAGNOSIS_REQUEST_LIMIT_MS`。配置关闭时隐藏对话式入口或回退到只读提示；限流间隔可以按演示或生产环境调整。

6. **测试以业务行为为中心。**

   使用 Vitest 和 React Testing Library 测试对话流程、API 编排、错误提示、按钮禁用、限流和配置开关。相比只做快照测试，行为测试更能保障诊断闭环不被 UI 重构破坏。

## Risks / Trade-offs

- **前端状态机过度复杂** -> 仅覆盖诊断闭环需要的阶段，避免引入重量状态库，先用 reducer 和纯函数建模。
- **后端接口耗时导致用户误以为卡住** -> 对运行中的任务展示明确状态和不可重复提交按钮，并保留错误重试入口。
- **重复点击产生多份报告或恢复动作** -> 前端同名任务锁和限流先拦截；后端已有会话归属校验，后续可补充幂等键。
- **配置开关遗漏导致测试环境行为不稳定** -> 配置读取集中在一个模块，测试中显式覆盖默认值。
- **中文注释与英文代码混杂影响可读性** -> 业务命名、函数和变量保持英文；仅在状态机、并发锁和配置边界处用中文注释说明意图。
## Addendum: Internationalization and Tips Design

1. **采用轻量前端 i18n 字典，不引入重量国际化框架。**

   初版只需要默认中文和可扩展资源结构。实现应新增集中 `i18n` 模块，提供 `t(key)` 或等价方法读取文案。所有用户可见文案通过 key 管理，默认资源为 `zh-CN`。如果后续需要英文或运行时切换语言，可以在同一结构中扩展 locale 资源。

2. **对话消息也通过 i18n key 派生。**

   工作流中的 system/user/assistant 消息不应直接拼接不可维护的硬编码中文。需要将固定模板放入 i18n 字典，动态值如 session id、状态、证据类型通过参数插值。

3. **关键控件 tip 统一用可访问属性和可见辅助文本表达。**

   按钮和输入框应至少提供 `title` 或 `aria-describedby`，关键输入应有短辅助说明。tip 内容也通过 i18n 字典管理，避免中文文案散落在组件中。

4. **测试以默认中文和 tip 存在为验收点。**

   前端测试应验证默认中文文案展示、关键按钮和输入框存在 tip，以及主要流程仍能通过中文 UI 完成。

风险：

- **文案 key 过多导致维护成本升高** -> 仅对用户可见文案建 key，业务枚举值可先通过小型 label map 转换。
- **tip 过长影响界面密度** -> 长说明使用 `title` 或辅助文本，按钮正文保持简短。
