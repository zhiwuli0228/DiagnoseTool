## Why

Thread Doctor MVP 当前实现已经覆盖故障会话、证据采集、诊断报告、恢复建议和复盘卡片，但原变更文档仍要求 MySQL/JPA 持久化。当前能力定位为轻量诊断闭环，不应引入数据库依赖；所有运行态数据应保存在应用缓存中，关键结果由用户在前台操作后导出为结果文档。

## What Changes

- 将 MVP 的数据存储约束从 MySQL/JPA 持久化调整为应用内缓存，故障会话、证据、指标、诊断报告、恢复建议和复盘卡片均不写入数据库。
- 保留现有 REST API 和诊断闭环能力，不扩大到历史知识库、长期检索或生产级持久化。
- 将“复盘卡片/关键结果沉淀”调整为前台用户触发后的结果文档输出，文档内容来自当前缓存中的会话上下文。
- 移除设计和任务中关于 MySQL JDBC、JPA Entity、持久化表、真实数据源连接的要求。
- 新增缓存失效和容量边界要求，避免缓存数据被误认为长期可信存储。

## Capabilities

### New Capabilities

- `incident-session`: 管理故障会话生命周期、状态流转和会话详情查询，数据仅保存在应用缓存中。
- `evidence-management`: 上传、缓存、查询和归一化故障证据，并与当前缓存中的故障会话关联。
- `jstack-analysis`: 解析 jstack 文本并输出线程状态、锁竞争、热点堆栈和阻塞模式分析结果。
- `metrics-snapshot`: 缓存 JVM、Redis、Kafka 和 DB 连接池指标快照，作为当前诊断上下文输入。
- `fault-pattern-detection`: 基于结构化证据和指标识别候选故障模式，并输出置信度和证据引用。
- `diagnosis-report`: 结合规则检测、证据链和 LLM 推理生成结构化诊断报告，报告仅缓存在当前会话中。
- `recovery-recommendation`: 生成风险分级恢复建议，支持 MVP 模拟执行和恢复验证说明。
- `incident-card-memory`: 基于当前会话生成 Markdown 结果文档，不写入数据库或长期知识库。

### Modified Capabilities

- 无。本 change 仍处于未归档状态，直接修正本 change 的新增能力约束。

## Impact

- 后端需移除数据库作为运行前置条件，改用缓存仓储实现替代 JPA 仓储。
- 配置需移除或禁用默认 MySQL 数据源要求，生产和本地调试均不依赖数据库。
- API 契约保持聚焦：会话、证据、指标、诊断、恢复和结果文档生成接口仍服务当前诊断闭环。
- 测试需验证缓存仓储、缓存失效、无数据库启动、结果文档生成和现有诊断闭环。
