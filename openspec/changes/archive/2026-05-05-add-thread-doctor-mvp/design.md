## Context

当前代码已经存在 Spring Boot 后端和 React 前端，部分实现使用 JPA Repository、实体注解和 MySQL 配置。新的约束要求 Thread Doctor MVP 不使用数据库：所有运行态数据只保存在缓存中；诊断报告、恢复建议、复盘卡片等关键结果需要在用户前台触发后以结果文档形式输出。

这次调整只修正 `add-thread-doctor-mvp` 的存储和结果输出边界，不新增长期知识库、搜索、审计、权限或生产写操作。

## Goals / Non-Goals

**Goals:**

- 用缓存仓储替代数据库仓储，覆盖会话、证据、指标、诊断报告、恢复动作和复盘卡片。
- 保持现有诊断闭环 API 能力，避免前端和测试因存储层调整出现不必要的契约变化。
- 移除 MySQL/JPA 作为运行、测试和本地调试前置条件。
- 在前端用户触发后输出 Markdown 结果文档，文档包含诊断结论、证据摘要、恢复建议和验证方式。
- 为缓存容量、过期时间和清理策略提供配置开关，默认适合本地调试。

**Non-Goals:**

- 不实现数据库持久化、历史知识库、全文检索或跨进程数据共享。
- 不实现真实生产恢复动作，恢复动作仍仅支持模拟执行。
- 不新增复杂权限、审批、租户隔离或审计能力。
- 不改变 LLM 接入方式，仍通过 OpenAI-compatible REST Client 抽象。

## Decisions

1. **使用应用内缓存仓储替代 JPA 仓储。** 现有服务层已经依赖仓储接口语义，最小修改方案是保留服务调用方式，移除 `JpaRepository` 继承和实体注解，改为基于 `ConcurrentHashMap` 或 Spring Cache 的缓存实现。这样不会扩大 API 范围，也避免引入数据库迁移。

2. **缓存数据是运行态数据，不承诺长期保存。** 缓存仓储需要支持按会话 id 查询当前闭环所需数据，并通过配置控制最大条数和 TTL。服务返回值和前端文案必须避免暗示“长期沉淀”或“知识库持久化”。

3. **关键结果通过前台触发生成结果文档。** 复盘卡片能力继续使用 Markdown 作为输出格式，但定位从“持久记忆”调整为“当前会话结果文档”。前端在用户点击生成后展示文档内容，并可使用浏览器能力复制或下载，不需要后端写文件或落库。

4. **移除数据库默认配置。** `application.yml`、`application-local.yml`、`application-prod.yml` 不应默认配置 MySQL 数据源。生产环境如果部署该 MVP，也应使用缓存配置，而不是要求数据库地址、账号或表结构。

5. **测试优先覆盖无数据库运行。** JUnit5 + Mockito 测试应验证服务通过缓存仓储工作；Spring API 测试应能在没有 MySQL 的环境启动。前端测试覆盖结果文档生成入口和展示。

## Risks / Trade-offs

- **进程重启后数据丢失** -> 在设计和 UI 文案中明确缓存数据仅用于当前诊断会话，关键结果由用户导出文档保存。
- **缓存容量失控** -> 增加最大会话数、TTL 和清理策略配置，默认值偏保守。
- **现有 JPA 代码改动范围较散** -> 只替换仓储和模型注解，不改诊断算法、LLM、恢复建议等业务流程。
- **用户误以为结果已入库** -> API 和前端文案统一使用“生成结果文档”，避免“保存到知识库”等表述。
